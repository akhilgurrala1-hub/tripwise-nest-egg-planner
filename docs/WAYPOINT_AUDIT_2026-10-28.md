## Decision

Keep improving this application. It has a usable planning interface and a substantial budget engine, but it is still a prototype. Do not describe it as a fully verified travel platform or launch it broadly yet. Fixes in this branch are isolated from production and have not been deployed.

The latest GitHub code and the published app differ: the website rendered its sample dashboard, while the pinned source had a reproducible savings-calculator error. A successful build alone did not catch that error. The exact source revision deployed to Lovable was not available, so this audit does not assume they are identical.

## Budget correctness and practical limits

The engine works in cents and computes transportation, gas, group/day/night multipliers, taxes on configured taxable categories, and miscellaneous cushion. Reserve is carved out before planned spending. Stops are intentionally outside tax/cushion calculations so their incremental budget effect equals their estimated cost. Existing tests cover normal car/flight/rental calculations, overrides, reserve invariants, stop cost and reduction suggestions.

The branch fixes the store/UI integration around that engine rather than replacing its financial model. Linked sightseeing uses cent-rounded item costs. Changing linked activities recalculates taxes/cushion using the same calculator. Savings are evaluated by recomputing the complete budget, including custom tax/cushion overrides, and the combined savings figure is checked against applying every shown tip.

Limits remain: USD only; destination taxes are samples; real driving distance is not imported; stop fuel uses a sample 35 mph detour assumption; multiple independent detours are summed rather than jointly routed; meal/activities allowances and road-stop charges can overlap conceptually. Real Google listing price ranges are treated as USD estimates without validating currency. Breakfast, baggage, resort fees, insurance, cancellation terms, airport transfers, accessibility needs and other costs are not comprehensively modeled. These are not verified live trip quotes or a guaranteed spending ceiling.

## Security and database review

- Current `.env` contains Supabase URL/project/publishable configuration and a browser Maps key/tracking ID. No private Lovable AI key, server Maps key or Supabase service-role secret was found there. Public browser keys are visible by design; their actual restrictions and quotas were not available to inspect. No secret rotation was performed. This is a current-tree check, not a complete historical secret scan.
- The generated service-role client is server-only and no current app route imports it. Preserve that separation. User operations should use verified user credentials and RLS, not an admin client.
- The trips migration enables RLS and declares owner-only SELECT/INSERT/UPDATE/DELETE policies, including `WITH CHECK` for writes. It also uses an owner-preserving update trigger. This is sound intent in source, not proof it is applied to the live database.
- The table grants authenticated DELETE and the policy allows hard deletion. Implement product deletion as a soft-delete using `deleted_at` and a recovery flow before exposing it. Test isolation with two staging accounts and an anonymous client. Review inherited grants, migrations, backup/restore and schema-version behavior.
- `drizzle/schema.ts` is intentionally empty while a hand-written SQL migration exists. Do not blindly regenerate schema or run push/migrate against production. The generated trips types do not prove that saving is connected or that the migration was applied.
- Existing CSRF middleware is present. The branch reuses verified-claims auth middleware for AI and hardens redirect validation against backslashes/control characters. Mocked tests check declaration of auth on both billable functions and claims rejection/acceptance. They do not certify the production auth service.
- Require durable per-user limits, request-size limits, concurrency limits, project spend caps and provider quotas before a public launch. Authentication alone does not bound bills. Avoid using in-memory counters as a cross-instance guarantee.
- Gateway/AI errors are logged, sometimes with raw provider error bodies. Review redaction and retention before real customer trip/location data is processed. Generic public errors are preferable to exposing internal configuration details.

## Safe update and rollback procedure

- This branch contains no production credential changes, applied migrations, new paid services, dependency upgrades or deployment step. Existing working page structure and semantic design tokens are retained.
- Review and preview the branch first. The new CI workflow is verification-only, with read-only repository permissions; it does not deploy. Make these checks required through repository settings when ready.
- Before releasing the v3 local storage format, test v1/v2 imports and export/back up representative local trips. The new code reads v1/v2 and writes v3. Older v2 code cannot read v3: a rollback after rollout therefore needs a compatibility patch/export plan, not just restoring the old code. No production trip data has been migrated by this work.
- Deploy only after approval, retain the previous deployment artifact, record the deployed commit, smoke-test server functions, monitor errors/costs and verify both data and code rollback behavior. Do not rewrite published Git history or push fixes directly to `main` without review.
